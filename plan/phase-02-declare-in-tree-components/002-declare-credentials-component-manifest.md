# Declare Credentials Component Manifest

## Purpose and scope

Populate the `credentials` entry of `plugable.host.builtins[0].components` in `core-server`'s `package.json`, derived from `src/credentials/setup.mjs` and its readers. This is the highest-value entry in the phase: it declares the in-tree half of the `ynGa` (`serverHome` → `serverConfigRoot`) rename bug, and the provider half of the GITHUB_API load-ordering gap. This task's scope is limited to the `credentials` array entry; the `controls` and `issues-github` entries are separate, independent tasks ([001](./001-declare-controls-component-manifest.md), [003](./003-declare-issues-github-component-manifest.md)) touching the same file's other array entries.

This task assumes Phase 1 has already landed the empty, structure-only `components` array (see task 001's Purpose and scope for the same assumption, stated once there in full).

## Requirements

- In `package.json`, locate the `components` array entry for `"component": "credentials"` and populate its `provides` and `requires`. Re-derive from real source rather than transcribing [plugin-set-inventory.md](../notes/plugin-set-inventory.md)'s draft unread; the draft, as a checkpoint:
  - `provides`:
    - `{ capability: appExt:credentialsDB, phase: load, via: 'src/credentials/setup.mjs — app.ext.credentialsDB = <bare assignment>' }` — this is what makes the GITHUB_API ordering gap's provider side declarable. `credentials` is component index 1 (0-based within its entry, or whatever the real Phase-1-authored index is — verify against the actual array) inside the first, and only, `builtins` entry, so this provide's `loadIndex` is provably ahead of any Server-Package-Root source.
    - `{ capability: pathVar:credential, phase: load, via: "src/credentials/setup.mjs — registerPathVar('credential')" }`
  - `requires`:
    - `setupArg:app`, `setupArg:cache`, `setupArg:registerPathVar`
    - `setupArg:serverConfigRoot` — **this is the `ynGa` surface.** `src/credentials/setup.mjs:6` destructures `{ app, cache, registerPathVar, serverConfigRoot }` from the `setup()` argument object; a framework rename that removes the name yields `undefined` at destructure with nothing to fault on. Declaring this `requires` against `setupArg:serverConfigRoot` (fixed `framework`-phase provide, fixed `load`-phase require per the schema's reserved-kinds table) is what turns that silent `undefined` into a build-time `unsatisfied` finding naming this component.
    - `{ capability: appExt:serverConfigRoot, phase: runtime, reason: 'handlers/credentials/import.mjs reads it' }` — the second, runtime-phase reader; re-verify the exact file/line against real source.
- **Do not declare a `credential:GITHUB_API` provide.** `src/credentials/setup.mjs` constructs an empty `CredentialsDB` and registers no credential type; the actual registrar is `@sdlcforge/dev-core`'s `projects` component (confirmed against `/Users/zane/playground/sdlcforge/dev-core/package.json`'s `"plugable"` block, `projects` component's `provides`, which declares `credential:GITHUB_API @ load` via `setupCredentials()`). Declaring a provide `core-server` does not perform would be a false claim in a graph whose entire value is that its claims are true. Verify this omission is what the finished JSON actually contains (see Validation).
- **Record the transitive-coverage relationship for `@liquid-labs/liq-credentials-db` in a source-code comment, not in `package.json`.** `package.json` is strict JSON with no comment syntax, so there is no way to place a note "beside" the JSON declaration itself. Add a short comment at the `CredentialsDB` construction site in `src/credentials/setup.mjs` stating that `liq-credentials-db` receives `serverConfigRoot` as an ordinary constructor argument (never touching `app.ext`, never seeing the `setup()` argument object directly), so no capability kind names it, and that this component's own `setupArg:serverConfigRoot` requirement is the coupling that stands in for it: if the framework drops that name, this component fails and `liq-credentials-db` fails with it. Without this written down, a future reader could conclude the manifest has nothing to say about `liq-credentials-db` and would be wrong about why.
- **Do not declare `appExt:serverConfigRoot` as a provide of this component.** `appExt:serverConfigRoot` is provided by `@liquid-labs/plugable-express`'s own intrinsic manifest (`framework` phase, ships with the framework itself) — not by `credentials`. This matters beyond `core-server`'s own tree: `@sdlcforge/dev-core`'s `work` component independently requires `appExt:serverConfigRoot @ load` (confirmed in dev-core's `package.json` `"plugable"` block), and that requirement resolves against the framework's intrinsic provide, not against anything this task authors. If an earlier draft or dispatch note is read as implying `credentials` must "satisfy" `appExt:serverConfigRoot`, that is imprecise — the two capabilities this component's declarations are actually responsible for are `appExt:credentialsDB` (satisfying `dev-core`'s `projects` component) and its own `setupArg:serverConfigRoot`/`appExt:serverConfigRoot @ runtime` *requirements* (the `ynGa` in-tree consumer side), not a `serverConfigRoot` provide of any kind.
- Confirm every capability's `phase` against `docs/plugin-manifest-schema.md`'s reserved-kinds table (`setupArg:` is fixed `framework`/`load`; `appExt:` requires an explicit `provides` phase, `requires` defaults to `runtime`; `pathVar:` `provides` phase defaults to `load`).

## Validation

- Confirm `package.json` remains valid JSON after the edit.
- Re-read `src/credentials/setup.mjs` and `src/credentials/handlers/import.mjs` (or wherever the runtime `appExt:serverConfigRoot` read actually lives — confirm the exact path, since it was cited from a draft) and confirm every `provides`/`requires` entry traces to a real site.
- Grep the finished `credentials` component entry for `credential:GITHUB_API` and `appExt:serverConfigRoot` under `provides` — neither should appear; a match means a false provide was added and must be removed.
- Confirm the `src/credentials/setup.mjs` comment (or wherever the `CredentialsDB` is constructed) is present and states the `liq-credentials-db` transitive-coverage relationship in terms a reader unfamiliar with this plan can follow.
- If `node_modules/.bin/plugable-express-validate` is present, run `node_modules/.bin/plugable-express-validate --package-root . --format text` as a sanity check; a `manifest-invalid` or `exclusivity-disagreement` finding naming `credentials` is a real defect. Findings naming the still-empty `controls`/`issues-github` entries (if those tasks haven't landed yet) are expected and not this task's concern.
- `make test` / `make qa` are not expected to change behavior from this task alone — the validator is not wired into the build until Phase 4.
