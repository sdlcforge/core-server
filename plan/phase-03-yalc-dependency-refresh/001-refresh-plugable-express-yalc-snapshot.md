# Refresh Plugable-Express Yalc Snapshot

## Purpose and scope

Refresh `core-server`'s yalc-linked local snapshot of `@liquid-labs/plugable-express` (currently `.yalc/@liquid-labs/plugable-express/` in the main checkout) so it picks up the corrected package produced by `pluggable-express`'s own rename plan — specifically its phase 1 task 002 (`rename-github-repo-and-package-urls`, fixes `package.json`'s `repository`/`bugs`/`homepage` URLs) and task 004 (`fix-makefile-fragment-and-main-field`, fixes `package.json`'s `main` field and the actual dist build output filename from `dist/pluggable-express.js` to `dist/plugable-express.js`). No dependency-spec string change is needed — `core-server`'s `package.json` already declares `"@liquid-labs/plugable-express": "file:.yalc/@liquid-labs/plugable-express"`, a local yalc link, and the `.yalc/@liquid-labs/plugable-express/` folder is already single-g. This is a dependency-refresh task, not a rename task: it follows the exact procedure already documented in this project's [`CLAUDE.md`](../../CLAUDE.md) "Yalc Local Development" and "Dependency Updates" sections, and validates that the refresh actually corrects the snapshot's remaining double-g content (a stale copied `dist/pluggable-express.js`, and double-g `package.json`/`README.md` fields) as a side effect of `yalc` re-copying the upstream package, rather than hand-editing anything under `.yalc/`.

## Requirements

1. **Confirm the precondition.** Before starting, confirm `pluggable-express`'s own plan (`pluggable-express-rename`, phase 1 `framework-naming-cleanup`) has task 002 (`rename-github-repo-and-package-urls`) and task 004 (`fix-makefile-fragment-and-main-field`) both merged. If either is not yet merged, halt and report rather than proceeding — refreshing against an unfinished upstream rename would just re-copy the same stale double-g dist filename and produce a false-negative validation pass.

2. **Locate the upstream repo's current path.** `pluggable-express`'s own phase 1 task 001 (directory rename) may or may not have run yet by the time this task executes, and its own task doc explicitly leaves that sequencing to the manager. Do not hardcode either path — check which of these exists before proceeding:
   - `/Users/zane/playground/liquid-labs/plugable-express` (post-rename)
   - `/Users/zane/playground/liquid-labs/pluggable-express` (pre-rename)

   Use whichever one exists as the source for the next step. (If somehow neither exists or both exist, halt and report — that is an unexpected state this task should not guess through.)

3. **Push the refreshed package.** From the upstream repo's current location (per step 2), run:

   ```bash
   yalc push
   ```

   This runs the upstream repo's own `prepack` (`make build`) first, then republishes the local yalc snapshot and pushes it into every consumer that has previously run `yalc add` for this package — which includes `core-server`'s main checkout.

4. **Refresh `core-server`'s local snapshot and lockfile.** In `core-server` (the main checkout, or whatever worktree this task is executing in — see the note below if `.yalc/` is not yet present there), run:

   ```bash
   ./scripts/provision-local-deps.sh --refresh-lock
   ```

   This is the sanctioned equivalent of `rm -f bun.lock && bun install` per `CLAUDE.md`'s "Dependency Updates" section, with the added benefit of first copying `.yalc/` in from the main checkout if the current directory doesn't already have it (relevant if this task is dispatched into a fresh task worktree rather than run directly in the main checkout, since fresh worktrees start with no `.yalc/` per this plan's `dependencies_installed: not installed` precondition). Do **not** use a bare `bun install` — per `CLAUDE.md` and `docs/architecture.md`, Bun caches a `file:` dependency's own transitive-dependency graph in `bun.lock` and will not refresh it (or pick up a changed dist filename) on a bare `bun install`, `--force`, or a version bump; only removing `bun.lock` first forces re-resolution.

5. **Rebuild.**

   ```bash
   bun run build
   ```

6. **Verify tests and server startup still pass** against the refreshed dependency:

   ```bash
   bun run test
   bun run test:local
   ```

7. **Do not hand-edit anything under `.yalc/@liquid-labs/plugable-express/`.** That directory is fully regenerated by `yalc push`/`bun install`; if step 4's refresh still shows double-g content afterward (see Validation below), that means the upstream fix has not actually propagated — treat it as a signal to re-check the precondition (step 1) and/or re-run `yalc push`, not as something to patch by hand in `.yalc/`.

8. **Do not touch** `plan/manifest.yaml`, `plan/waves/sdlcforge-modernization/manifest.yaml`, `.flow/plans/pluggable-express-rename.json`, or historical plan documents under `plan/plan-summary-*.md` / `plan/notes/*.md` — these are plan bookkeeping / historical record, out of scope for this task even though they contain the string "pluggable-express".

## Assumptions

- **Cross-repo shell-out.** Step 3 requires running a command in a sibling project's repository (`plugable-express`/`pluggable-express`), outside `core-server`'s own worktree. If the executing task-agent's environment does not permit shelling out to a path outside its assigned worktree, the manager should run step 3 directly immediately before dispatching this task (mirroring the precedent set by `pluggable-express`'s own manager-executed directory-rename task, `phase-01-framework-naming-cleanup/001-rename-project-directory.md`), and this task's own execution then starts at step 4 with the push already done. This is flagged to the manager in this planning invocation's structured report rather than resolved here, since the actual constraint depends on the task-agent's runtime environment at dispatch time, not on anything this plan can determine in advance.
- **Fresh worktree with no dependencies installed.** Per this plan's `dependencies_installed: not installed` precondition, this task's own worktree starts with neither `node_modules/` nor `.yalc/`. Step 4's use of `scripts/provision-local-deps.sh` (rather than a bare `rm -f bun.lock && bun install`) accounts for that by bootstrapping `.yalc/` from the main checkout first.
- **Upstream state at planning time.** At the time this plan was authored, `core-server`'s main-checkout `.yalc/@liquid-labs/plugable-express/` still showed the pre-rename state (`package.json` `main: "dist/pluggable-express.js"`, double-g `repository`/`bugs`/`homepage` URLs, and a `dist/pluggable-express.js` file) — confirmed by direct inspection. This task's Validation steps are written against the expected post-refresh, post-upstream-rename state, not the state observed at planning time.
