# Wire Plugin Graph Build Gate

## Purpose and scope

Turn the manifest declarations Phases 1-2 authored into an **enforced** build gate: a hand-authored
`make/56-plugin-graph.mk` fragment appending to `TEST_TARGETS`, backed by a Jest test that drives the
framework's exported `validatePluginSet()` against `core-server`'s real, full plugin graph. This task also
authors a small, reusable test helper that resolves `core-server`'s real package root from inside a
`test-staging/`-run Jest test — used by this task's own gate test and reused, unmodified, by tasks
002-004 in this phase.

This task touches `make/*.mk` (`developer-make` conventions) and `src/lib/test/*.mjs`/`*.js` (`developer-node`
conventions). No other task in this phase depends on anything except this task's shared helper, so this task
must land first; tasks 002, 003, and 004 are parallel-eligible with each other once this task is done.

## Requirements

1. **Author `make/56-plugin-graph.mk`**, mirroring both this plan's own recipe
   ([`plan/notes/build-wiring-and-dependency-refresh.md`](../notes/build-wiring-and-dependency-refresh.md)'s
   "Build wiring" section) and the upstream precedent at
   `/Users/zane/playground/liquid-labs/plugable-express/make/56-plugin-graph.mk` (read it directly before
   writing this fragment — it is the working example this plan explicitly follows):
   - `CATALYST_PLUGIN_GRAPH_MARKER:=$(QA)/.plugin-graph.passed` (`$(QA)` is already defined by
     `make/10-locations.mk`).
   - `TEST_TARGETS+=$(CATALYST_PLUGIN_GRAPH_MARKER)` — **not** `BUILD_TARGETS`. This is what reaches both
     `make test` and `make qa` (`qa: test lint`, `make/95-final-targets.mk`) with one line and no edit to any
     Catalyst-generated fragment.
   - The marker's own recipe depends on the shared Jest pass-marker target `make/55-test.mk` already defines
     (read `make/55-test.mk` first and use its exact target name — do not guess or hand-roll a second Jest
     invocation) and simply `touch`es itself once that dependency succeeds — the same "the Jest test itself is
     the gate; the marker is bookkeeping" shape the upstream fragment uses. No dependency on `dist/`: this gate
     reads `node_modules` and `package.json`, both present immediately after install, and a broken plugin graph
     must be discoverable before a build is attempted.
   - **The banner must be inverted, explicitly.** Every other `make/*.mk` fragment in this repository says
     "generated by @liquid-labs/catalyst-*"; this one must say plainly that it is hand-authored and not
     Catalyst-generated, or a future Catalyst regeneration pass will read it as stale output and remove it.
   - `56` is deliberate — it sits in the numbering gap between the `55-*` fragments and `95-final-targets.mk`,
     so `include make/*.mk` (`Makefile`) picks it up with no edit to a generated file or to `Makefile` itself.

2. **Author the shared package-root helper** at `src/lib/test/helpers/resolve-plugin-set.mjs` — a new
   subdirectory alongside the existing `src/lib/test/fixtures/` (which already holds a non-`*.test.*` support
   module, `probe-plugin.mjs`, imported successfully by `builtin-plugins.test.js`; this is the established,
   working precedent for a non-test helper living under `src/lib/test/` and being picked up by the Babel/Jest
   pipeline). Export at minimum:
   - A `resolveCoreServerPackageRoot(testFileDirname)` (or equivalently named) helper computing the real repo
     root from a calling test file's own `__dirname`. Reuse the exact walk-up pattern already proven correct in
     this codebase — `app-init.test.js` and `full-tier-baseline.test.js` both do
     `fsPath.join(__dirname, '..', '..', '..', ...)` from a file at `src/lib/test/*.test.js` (compiled to
     `test-staging/lib/test/*.test.js`) to reach the repo root. Document in a comment that any caller must sit
     at that same depth (`src/lib/test/*.test.js`, one level deep — not `src/lib/test/helpers/*.test.js`) for
     the walk-up count to be correct, and take the walk-up count as an explicit parameter rather than hardcoding
     `..`/`..`/`..` inside the helper if any consumer might sit at a different depth.
   - A `readCoreServerPackageJSON(repoRoot)` helper (`JSON.parse(fs.readFileSync(fsPath.join(repoRoot,
     'package.json'), 'utf8'))`) — reused by tasks 002-004, which all need the parsed `package.json` to call
     `readHostDeclaration()` against.
   - This helper module does **not** wrap `validatePluginSet()` itself — each test file calls that directly
     with the `packageRoot` this helper resolves, since only this task's own gate test needs the full composed
     call, while tasks 002/003 need `readHostDeclaration()`/`resolvePluginManifest()` instead (see their own
     task docs). Keep this helper narrowly scoped to path/package-root resolution only.

3. **Author `src/lib/test/plugin-graph-gate.test.js`**, the Jest test that exercises the build-time gate over
   `core-server`'s real, full plugin graph (all of Phases 1-3 are assumed landed by the time this task runs —
   confirm this before starting; if `package.json` has no `plugable.host` block yet, halt and report rather than
   authoring a gate test against a graph that does not exist yet):
   - `import { validatePluginSet } from '@liquid-labs/plugable-express'`.
   - Call `validatePluginSet({ packageRoot: <resolved via the helper above> })` with no other options (default
     `strictOptional`/`strictOrder`/`checkLock`, matching what `make/56-plugin-graph.mk`'s gate should enforce
     day-to-day — do not silently tighten the gate beyond what the plan's declarations were authored against).
   - **Scope decision (manager, 2026-09-03), superseding this Requirement's original unconditional assertion
     below.** A first attempt at this task found the real graph is not fully clean: `validatePluginSet()`
     returns exactly 2 error-severity findings, both inside `@sdlcforge/dev-core#orgs` and unrelated to
     `core-server`'s own declarations — `[unsatisfied] appExt:_liqOrgs.orgSetupMethods` (traces to an
     out-of-tree `liq-policy` package) and `[violated-by-source-order] appExt:_liqOrgs.orgs` (a load-order
     fact about `dev-core#orgs` vs. `core-server#controls`, not a defect in either component's own
     declaration). Phase 3 already found and explicitly scoped both as `@sdlcforge/dev-core`'s own concern,
     outside this plan-group's `plans: {core-server: ...}` participant set (see
     [`plan/notes/manifest-ownership-boundary.md`](../notes/manifest-ownership-boundary.md)). Rather than
     asserting unconditional `outcome === 'ok'` (which would make `make test`/`make qa` permanently red for a
     condition this plan-group has decided not to fix from `core-server`'s side) or silently weakening the
     assertion to pass anything, assert an **explicit allowlist**: exactly these 2 known error-severity
     findings are permitted, matched by their finding-type + the specific capability/component names above —
     any additional or different error-severity finding must still fail the gate. This keeps the gate strict
     against any real regression (including a future change to `dev-core#orgs` that alters this specific
     finding set, which should force a fresh look rather than silently continuing to pass) while not blocking
     on an already-triaged, out-of-plan-group issue. In addition to the allowlist check:
     - Assert the two edges this plan-group actually chartered and Phase 3 verified —
       `@sdlcforge/dev-core#projects`'s `appExt:credentialsDB @ load` requirement and `@sdlcforge/dev-core#work`'s
       `appExt:serverConfigRoot @ load` requirement — both resolve satisfied (per Phase 3's own verified verdict
       shapes: literal `orderVerdict: 'satisfied-by-source-order'` for the first; edge-present-plus-no-failure-
       finding for the second, whose `orderVerdict` is `null` by schema design for that cross-phase pair — do not
       flatten this into asserting a literal `'satisfied'` string for the second edge).
     - Assert `result.exitCode === 1` (not `0`) given the allowlisted findings remain present, and record this
       explicitly as the expected steady-state exit code in a comment, so a future reader does not mistake `1`
       for an unexpected failure.
   - Assert the **stated coverage boundary**: `result.coverage.sourcesSearched` should include `'builtinPlugins'`
     and `'serverPackageRoot'` and should **not** claim coverage of `dynamicPluginInstallDir`/`pluginPaths` — read
     the actual shape `resolvePluginSet`'s `coverage` object returns (via `result.coverage`) before writing this
     assertion, rather than guessing the exact field names; this is the same boundary
     [`plan/phases/validation-gate-and-regression.md`](../phases/validation-gate-and-regression.md)'s Outputs
     section requires the gate to state in its own output. `core-server` passes `dynamicPluginInstallDir:
     COMPLY_HOME()` today (`src/lib/app-init.mjs`), so this is a live, non-hypothetical distinction for this
     host — confirm the coverage statement actually reflects that boundary rather than implying whole-set
     coverage.
   - Assert `result.engineResult.nodes.length` is non-trivial (not a vacuously empty graph) — e.g. it includes
     `@sdlcforge/core-server#controls`, `@sdlcforge/core-server#credentials`, `@sdlcforge/core-server#issues-github`,
     and `@sdlcforge/dev-core#projects` among the resolved node IDs (confirm the exact `nodeId` format against
     the real result rather than assuming — `npmName#component` is the format `@sdlcforge/dev-core`'s own test
     suite uses, but verify).

4. **Demonstrate red, once, and record the result — this is a manual verification step, not a permanent code
