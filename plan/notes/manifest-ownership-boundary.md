# Manifest Ownership Boundary

## Purpose and scope

Works out which packages in `core-server`'s plugin set `core-server` may author a manifest **for**, which it may not, and what follows for the two bugs this plan-group is chartered to fix. The change request asked for this line to be drawn explicitly for the `ynGa`-consuming packages; the analysis generalizes to the whole set and surfaces one genuine limit in the upstream contract.

## The rule

A manifest lives with the package it describes — a root `plugable.yaml`, a `package.json` `"plugable"` block, or (for a `builtinPlugins` entry, which has no package root of its own) inline in the host's `plugable.host.builtins`. `core-server` may author a manifest only where it controls the package's source. It has no supported way to author one for a package it merely installs: `node_modules/` is install output, and `.yalc/` is a gitignored snapshot regenerated by `yalc push` from another repository. Editing either is not durable and is not a change this project can commit.

`core-server` owns **three of twelve** graph participants. The three it owns are one npm identity; the nine it does not are eight loaded plugins plus one non-plugin registrar.

Every one of the nine has a local checkout in the playground, so they are reachable in principle — but each is a separate project with its own plan state, and modifying them is outside this plan-group's participant set (`plans: {core-server: ...}` in the wave manifest). Reaching into them from here would be a silent scope expansion across eight repositories.

## The `ynGa` consumers, classified

The change request named four packages and asked which side of the line each falls on. Answering it needs one distinction the package names obscure: what the package *is today*, not what it was when `ynGa` was filed.

| Package named in the request | What it is now | Side of the line |
|---|---|---|
| `liq-credentials` | **Absorbed.** Its source is `src/credentials/`; the donor package is no longer installed. | **`core-server`'s.** Its `setupArg:serverConfigRoot` requirement is declared as an inline component and is fully covered by this plan. |
| `liq-integrations` | **Superseded.** Its functionality is built into `plugable-express`, and `load-plugins.js`'s `supersededPlugins` set skips it if a consumer still declares it. Not in `core-server`'s set. | **Neither's.** No manifest is needed or possible; the coupling ceased to exist when the framework absorbed it. |
| `liq-credentials-db` | Third-party npm dependency (`@liquid-labs/liq-credentials-db`), **not a `plugable-express` plugin**. It receives `serverConfigRoot` as an ordinary `CredentialsDB` constructor argument from `src/credentials/setup.mjs`. | **Third-party — but covered transitively.** No capability kind names a function parameter, and inventing one would mean declaring the whole cross-package call graph. `src/credentials/`'s own `setupArg:serverConfigRoot` declaration *is* the coupling that stands for it: if the framework drops that name, `src/credentials/` fails and `liq-credentials-db` fails with it. This must be stated in a comment beside the declaration, or a reader concludes the manifest has nothing to say about that package and is wrong about why. |
| `liq-work` | Third-party npm dependency, loaded as an `explicitPlugins` entry. Reads `app.ext.serverConfigRoot` inside its own `setup()`. | **Third-party, and not covered.** This is the gap. |

So of the four: one is fully `core-server`'s and covered, one is moot, one is third-party but transitively covered, and one is third-party and uncovered.

## The limit in the upstream contract

The upstream `plugable.host` block carries two host-sited capability lists:

- **`providedCapabilities`** — capabilities supplied by something outside the plugin graph (a `CredentialsDB` tier the host installs directly, an ops-provisioned secret, a sidecar).
- **`assumeProvided`** — the transition escape hatch: capabilities the host asserts are delivered by a plugin that has not been manifested yet. Upstream sites it at the host deliberately, "because the person blocked by an unmanifested third-party provider is the person who can act," and states that its lifetime is the transition window and "the guide's answer remains *manifest the provider*."

Both are **provider-side**. Both take "the same entry shape as a `provides`," and both require an explicit phase because a provides phase is always required-explicit. There is no host-sited counterpart for a third-party plugin's **`requires`**, and the engine's satisfaction pass only ever matches a `requires` against the union of provides, the intrinsic set, `providedCapabilities`, and `assumeProvided`.

That is a coherent design, not an oversight: it makes the host able to *unblock* a graph a third party has not manifested, without letting the host make claims about a third party's internals it cannot verify. But it has a direct consequence for this plan-group.

**Both bugs the change request leads with have their requiring half in a third-party package.**

| Bug | Requiring side | Providing side |
|---|---|---|
| `ynGa` (`serverHome` → `serverConfigRoot`) | `liq-work` requires `appExt:serverConfigRoot @ load` — third-party | `plugable-express` intrinsic manifest — upstream's, and it exists |
| GITHUB_API ordering gap | `liq-projects` requires `appExt:credentialsDB @ load` — third-party | `src/credentials/` provides it at `load` — **`core-server`'s, declarable here** |

`core-server` can declare the provider in the second row with a provable `loadIndex` (builtins are source #1; `credentials` is component index 1 within the entry). But a provide with nothing requiring it emits no finding. Declaring it alone does not close the gap; it only makes the fact writable.

The upstream plan says the same thing about `ynGa` in its own words, and the honesty is worth preserving here: "the mechanism only fires once those four consumers are manifested, which is the downstream `compile-time-manifest-sdlc-server` plan-group's work, not this one's." That sentence assumes this plan-group can manifest those consumers. For `liq-credentials` it can, because absorption moved the source in-tree. For `liq-work` and `liq-projects` it cannot, because they are other repositories.

**This is flagged for the manager rather than worked around**, per the change request's own instruction. It is not a defect in the upstream contract — nothing there is wrong — but it is a genuine gap between what the contract enables from `core-server` alone and what this plan-group is chartered to deliver.

## The options, with what each costs

Stated as options rather than a recommendation, because the choice is a scope decision and reshapes this plan's phase 3 entirely.

**A — Ask upstream for a host-sited overlay.** A `plugable.host.pluginOverlays` (or equivalent) letting a host declare a `requires` on behalf of an unmanifested third-party plugin, marked second-hand and unverifiable in exactly the way `onBehalfOf` marks a second-hand provide. Closes both bugs from `core-server` alone. Costs a schema addition to a plan whose design is finalized, so it must go back to the manager as a change request against `compile-time-manifest-framework`, not be patched here. Carries a real hazard upstream already named for `onBehalfOf`: a host can simply be wrong about a package it does not control, and a wrong `requires` produces a false failure rather than a false pass.

**B — Manifest the third-party plugins in their own repositories.** The correct answer by the upstream contract's own logic ("manifest the provider"), and the only one that produces verifiable declarations. Costs new plan-groups for `liq-orgs`, `liq-projects`, and `liq-work` — the three that carry real coupling; the other five are near-empty. Sequencing hazard: three of those repos are also participants in the wave's `dev-core-consolidation` plan-group, which merges them into a new `sdlcforge/dev-core` package, so manifesting them individually may be work done twice.

**C — Accept partial coverage now.** Declare what `core-server` owns, wire the gate, and let the eight third-party plugins stay unmanifested — which the framework treats as benign by design, so the gate runs green. Cheapest and lowest-risk, and it delivers a real result: the three absorbed-donor re-introduction conflicts, the in-tree half of `ynGa`, and a standing gate that catches every future regression in `core-server`'s own tree. Costs the two headline bugs: neither is closed, and the plan would not deliver its charter as written.

**D — B for `liq-projects` only.** `@liquid-labs/liq-projects` is already yalc-linked from a local checkout, so it is the one third-party plugin whose development loop is already wired into `core-server`. Manifesting it in its own repo closes the GITHUB_API gap — the one the change request calls a "hard `TypeError` if unmet" — for a single extra participant. Leaves `ynGa`'s `liq-work` half open.

A and B are not exclusive: A is the transition mechanism, B is the destination, and the upstream contract already frames `assumeProvided` in exactly that shape for the provider side.

## What is safe to build regardless of the answer

Everything `core-server` owns, and it is the majority of this plan's actual work:

- The `plugable.host` block with `explicitPlugins` and the three ordered builtin components.
- `verifyHostDeclaration()` in the Jest suite, so the declaration cannot drift from the real arrays.
- The `make/56-plugin-graph.mk` gate in `TEST_TARGETS`.
- The three in-tree component manifests, including the `ynGa` `setupArg:serverConfigRoot` requirement that a rename would break.
- A regression test asserting the absorbed-donor conflict is detected.

None of it changes shape under any of A-D. That is why this plan sequences it first and isolates the third-party question into its own phase.
