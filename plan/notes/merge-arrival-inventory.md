# Merge Arrival Inventory

## Purpose and scope

The measured, per-path disposition of `git merge --allow-unrelated-histories dev-core-source/main` into `@sdlcforge/core-server`'s `main`, produced by actually running the merge in a throwaway clone rather than by reading directory listings. It exists so Phase 2's implementer works from a verified arrival map instead of git's conflict list, which — as the consolidation contract warns and this note confirms in a different direction than expected — is not the list of files to review.

Every classification below was read from `git merge-tree --write-tree --allow-unrelated-histories --name-only`, a real `git merge --no-commit`, and blob-SHA comparison of the two trees, against `core-server` `main` at `4ded354` and `dev-core` `main` at `5d5c2a3`.

## How this was measured

```bash
git clone --no-hardlinks /Users/zane/playground/sdlcforge/core-server /tmp/merge-probe
cd /tmp/merge-probe
git remote add dev-core-source /Users/zane/playground/sdlcforge/dev-core
git fetch dev-core-source main
git merge-tree --write-tree --allow-unrelated-histories --name-only HEAD dev-core-source/main
git checkout -b merge-probe main && git merge --allow-unrelated-histories --no-commit dev-core-source/main
```

Neither project's own working tree was touched. The probe clone's merge was aborted after measurement.

## Headline correction to the phase plan

**The phase document's central premise about the generated build files is wrong, and wrong in the safer direction.** [`phases/absorb-dev-core.md`](../phases/absorb-dev-core.md) §2 and [`notes/pre-merge-state.md`](./pre-merge-state.md) both state that both repositories' `Makefile`, `make/*.mk`, and `.gitignore` "descend from the same Catalyst generator, so a byte-identical fragment merges silently with nothing to flag it."

They do not descend from the same generator. `core-server` is generated by `@liquid-labs/catalyst-lib-makefiles` / `@liquid-labs/catalyst-builder-node` (`CATALYST_*` variable prefix); `dev-core` is generated by `@liquid-labs/sdlc-projects-workflow-local-node-build` (`SDLC_*` variable prefix). **Every** shared build file differs, and **every** one produces an `add/add` conflict. Nothing in the build-file set merges silently.

Exactly one path in the entire merge is byte-identical on both sides and therefore merges with no conflict: `plan/manifest.yaml`, identical because the wave tooling wrote the same `sdlc-core-unification` plan registration into both repositories. It is content `core-server` already has, so the silent merge is a no-op and needs no handling.

This does not weaken the contract's underlying warning — it relocates it. The unreviewed-arrival hazard is entirely in the **clean-add** set (169 paths, listed below), not in the generated build files.

## Findings

### 1. Path classification

Covered by the tables above. The one-line summary: 13 conflicts, 1 silent identical merge (`plan/manifest.yaml`), 169 clean arrivals of which 10 need a decision and 159 are the absorbed component tree.

### 2. `Makefile`, `make/*.mk`, `.gitignore` are **not** byte-identical

Confirmed by direct diff — the premise is false. The two repositories sit on different generations of the toolchain:

| | `core-server` | `dev-core` |
|---|---|---|
| Generator | `@liquid-labs/catalyst-lib-makefiles`, `@liquid-labs/catalyst-builder-node` | `@liquid-labs/sdlc-projects-workflow-local-node-build` |
| Variable prefix | `CATALYST_*` | `SDLC_*` |
| Resource packages | `@liquid-labs/catalyst-resource-{babel-and-rollup,eslint,jest}` | `@liquid-labs/sdlc-resource-{babel-and-rollup,eslint,jest}` |
| Inventory file | `.catalyst-data.yaml` | `.sdlc-data.yaml` |

Diff sizes: `.gitignore` +3/−8, `Makefile` +3/−3, `10-locations.mk` +5/−3, `10-resources.mk` +11/−10, `15-data-finder.mk` +6/−5, `20-js-src-finder.mk` +8/−7, `55-lint.mk` +19/−17, `55-test.mk` +28/−24, `95-final-targets.mk` +8/−4.

**Recommendation.** This is good news for the merge — git surfaces all nine files rather than silently taking one side — and it means the phase's warning-driven verification step can be simplified: there is no silently-merged build file to hunt for. Resolve all nine `--ours`. Keep the blob-comparison verification anyway, but re-aim it: its real target is the 10-path clean-arrival set, which is where an unreviewed file can genuinely slip through. Correct the claim in [`phases/absorb-dev-core.md`](../phases/absorb-dev-core.md) §2 and [`notes/pre-merge-state.md`](./pre-merge-state.md) so a future reader does not go looking for a hazard that is not there and miss the one that is.

### 3. Clean-add confirmations

All four named paths confirmed as clean adds with no `core-server` counterpart: `src/index.mjs`, `make/50-dev-core-js.mk`, `.sdlc-data.yaml`, `package-lock.json`. Post-merge index state verified directly:

| Path | Post-merge blob | Same as `core-server` `main`? |
|---|---|---|
| `src/lib/index.js` | `e8791e8` | **Yes** — untouched |
| `bun.lock` | `901e082` | **Yes** — untouched |
| `.catalyst-data.yaml` | `41b9a23` | **Yes** — untouched |
| `src/index.mjs` | `6ee3342` | n/a — arriving, remove |
| `package-lock.json` | `e7c8a82` | n/a — arriving, remove |
| `.sdlc-data.yaml` | `c08438e` | n/a — arriving, remove |

Neither `src/lib/index.js` nor `bun.lock` can be overwritten by this merge: dev-core has no file at either path, so git never considers them. The overwrite risk the phase doc guards against does not exist mechanically; the risk that does exist is the *inverse* — dev-core's versions sitting alongside `core-server`'s under different names, inert but present, with `package-lock.json` next to `bun.lock` being the one that could actually mislead a later `npm install`.

`docs/architecture.md` is confirmed a genuine conflict: both sides are real, substantive, fully divergent documents (83 vs. 130 lines, sharing only the `# Architecture` heading and a `## Purpose and scope` section whose contents are entirely different). It is the only `docs/*` conflict; the other two arriving `docs/` files are clean adds and the three `core-server`-only `docs/` files are untouched.

### 4. Disposition of dev-core's package-level tests

Both were read in full and both were evaluated against `core-server`'s real post-merge conditions. `core-server`'s Jest config (`@liquid-labs/catalyst-resource-jest`) leaves `testMatch` at the default `**/?(*.)+(spec|test).js?(x)`, so both suites **will** be collected from `test-staging/test/` once Babel emits them. The `repoRoot = fsPath.resolve(__dirname, '..', '..')` walk in `plugin-manifest.test.mjs` still lands on the repository root under `core-server`'s identical `src` → `test-staging` layout, so it will successfully read `core-server`'s `package.json`. Nothing fails for a mechanical reason; the failures are all premise failures.

**`src/test/plugin-manifest.test.mjs` — drop. Do not port.**

It is a drift guard over `plugable.components[…]`, a **plugin-side** manifest shape that `core-server` does not have and will not have. `core-server`'s `plugable` block is a **host** declaration. I verified the actual behavior empirically against the installed `@liquid-labs/plugable-express`:

```text
resolvePluginManifest({ dir: <core-server>, pkg: <core-server package.json> })
  → 1 record, { npmName: '@sdlcforge/core-server', component: undefined }
validatePluginGraph({ records })
  → ok: true, counts: { error: 0, warning: 0, info: 0 }, findings: []
```

Against that, the suite's 17 assertions split three ways:

- **4 hard failures.** The manifest-parses test (`expect(records).toHaveLength(4)` gets `1`, and the `records.map(component)` ordering assertion gets `[undefined]`); the `pathVar:parameterKey` test (`records.find(component === 'orgs')` is `undefined`, so `orgs.provides` throws `TypeError`); the not-overall-clean test (`expect(result.ok).toBe(false)` — it is `true`); and the unsatisfied-set test (`findingsShape` is `[]` against 4 expected entries, and `result.counts` is all-zero against `{ error: 2, warning: 0, info: 2 }`).
- **12 vacuous passes — the dangerous half.** All twelve `test.each` satisfaction cases assert *the absence of a finding naming a triple*. With `findings: []`, every one passes while asserting nothing at all. A ported version of this suite would go green on an empty graph.
- **1 incidentally-still-true pass.** The `FRAMEWORK_MANIFEST`-is-folded-in sanity check.

Two further premises die on contact. The file's header comment says "There is no plugin-side equivalent of `verifyHostDeclaration()`… a plain plugin (dev-core) has neither" — post-merge the package *is* the host, and `verifyHostDeclaration()` is exactly the right tool. And its import comment insists `@liquid-labs/plugable-express` "is a devDependency (test-only import); it must never be… promoted to `dependencies`" — in `core-server` it is already a runtime `dependencies` entry (`file:.yalc/@liquid-labs/plugable-express`).

Most decisively, **the job is already done**. `core-server` carries `src/lib/test/host-declaration.test.js` (runs `verifyHostDeclaration()` against the real `builtinPlugins`/`explicitPlugins` arrays) and `src/lib/test/plugin-graph-gate.test.js` (runs `validatePluginSet()` over the real, full, resolved graph with an explicit error-finding allowlist). Those two cover both directions of manifest drift for the host shape, over the real graph rather than a package.json-only slice. The dev-core suite is superseded, not merely stale.

The one thing worth carrying forward is its *scoping discipline* — the "do not assert an overall-clean graph" rule and the reasoning behind naming the expected out-of-package gaps explicitly. `plugin-graph-gate.test.js`'s `ALLOWLISTED_ERROR_FINDINGS` block already embodies exactly that discipline, so this is a note to preserve when Phase 3 revises that allowlist (which it must: the second allowlist entry names `@sdlcforge/dev-core#orgs`, an nodeId that ceases to exist), not new code to write.

**`src/test/index.test.mjs` — drop in Phase 2, port the assertions in Phase 3.**

It cannot survive Phase 2 in any form: its first import is `from '../index'`, and `src/index.mjs` is being removed, so the suite fails at module load. But its assertions are the genuinely valuable half of dev-core's package-level testing, and every one of them has a direct analogue against `src/lib/builtin-plugins.mjs`, which is the merged package's aggregation boundary:

| dev-core assertion | Post-merge analogue | Adaptation needed |
|---|---|---|
| `handlers` is a fresh array, not an alias of any submodule's | Same, over `builtin-plugins.mjs`' `flatMap` result across 7 submodules | Mechanical. `builtin-plugins.mjs`' fact-1 comment makes this exact hazard explicit; it is currently unasserted. |
| No `(method, path)` pair registered twice | Same, across all 7 submodules' merged handlers | Mechanical, and **more valuable** post-merge: the 7-way merge is a strictly larger duplicate surface than the 4-way one. |
| The 4 `projects-audit` routes with exact paths | Same | Mechanical. |
| `projects-audit` contributes handlers but no `setup` | Same | Mechanical. |
| Composite `setup` runs submodules in fixed order and populates `app.ext` | Same, over `builtinPluginsFor(...)[0].module.setup` | **Needs adaptation.** The expected `registeredPathVars` grows to include `credential` (from `credentials`), and the expected `app.ext.setupMethods` list grows from `orgs`' 3 entries to include `controls`' 2 and `issues-github`' 1. The literal arrays cannot be copied. |
| `app.ext.constants.WORK_DB_PATH` exact key path; `workKey` `validationRe` | Same | Mechanical — these are `app.ext` contract-freeze assertions and stay valid verbatim. |

Recommended shape: Phase 2 `git rm`s the file, recording in the commit message that its assertions are carried into Phase 3's scope. Phase 3, in the task that wires the seven components into `builtin-plugins.mjs`, adds the adapted assertions to `core-server`'s **existing** `src/lib/test/builtin-plugins.test.js` rather than reconstituting a parallel `src/test/` tree. Writing them in Phase 2 is not possible: at merge time the four dev-core submodules are still inert and absent from the `submodules` array, so there is nothing for the aggregate assertions to assert against.

### 5. dev-core's `plan/` residue and the exact `git rm` set

dev-core's `main` tracks exactly four `plan/` paths — no `plan/waves/`, no `plan/phases/`, no `plan/notes/`, no `plan/TODO.yaml`, no `plan/resources/`. Those live only on dev-core's `plan/sdlc-core-unification` branch, which is not a merge source.

| dev-core path | Disposition | Handling |
|---|---|---|
| `plan/followups.yaml` | **Conflict** (`add/add`) | `git checkout --ours` — **not** `git rm`. Then re-file the still-relevant items separately (see the conflict table). |
| `plan/manifest.yaml` | **Identical merge** | Nothing. Byte-identical to `core-server`'s; the merge is a no-op. |
| `plan/plan-summary-dev-core-plugin-manifest.md` | Clean arrival | `git rm` |
| `plan/plan-summary-orgs-defects-remediation.md` | Clean arrival | `git rm` |

So the **entire** `plan/` `git rm` set is two paths:

```bash
git rm plan/plan-summary-dev-core-plugin-manifest.md \
       plan/plan-summary-orgs-defects-remediation.md
```

This is narrower than [`phases/absorb-dev-core.md`](../phases/absorb-dev-core.md) §2 states, which lists dev-core's `plan/` residue as "`followups.yaml`, `manifest.yaml`, and two `plan-summary-*.md` files." `followups.yaml` is a conflict resolution, and `manifest.yaml` is not residue at all. Removing either with `git rm` would delete a file `core-server` needs.

**On the "the merge runs inside a plan worktree" premise — this is not how the repository is actually laid out, and the difference matters.** `core-server`'s plan worktree at `worktrees/plan/sdlc-core-unification` is checked out on branch `plan/sdlc-core-unification`, and that branch *does* track a full `plan/` directory (`TODO.yaml`, `overview.md`, `phases/`, `notes/`, `resources/`, `waves/`, 23 paths). The absorption merge does not belong on that branch. It belongs on `main` or on a unit-of-work branch cut from `main` — and **`core-server`'s `main` tracks 14 `plan/` paths of its own** (`followups.yaml`, `manifest.yaml`, six `plan-summary-*.md`, five `plan/resources/*`, and `plan/waves/sdlcforge-modernization/manifest.yaml`).

So `plan/` is squarely inside the merge target tree, "plan/ residue" is a real hazard rather than a hypothetical one, and the phase document's existing warning stands and should be strengthened, not relaxed:

- **Never** `git rm -r plan/`. It would delete 14 of `core-server`'s own tracked planning files.
- **Never** `git rm plan/manifest.yaml` or `git rm plan/followups.yaml`. Both are `core-server`'s.
- The `git rm` set is the two `plan-summary-*.md` paths above and nothing else.

Note also that the stale local branch `work-sdlcforge/core-server/64` (at `84f1a87`, "wip: bun/npm migration in progress") tracks only `plan/manifest.yaml` under `plan/` and predates the current `main`. It is not a viable merge target and should not be reused.

## Adjacent observations

Noted, not acted on, and outside this note's scope:

- **Babel `--ignore` divergence in `make/55-test.mk`.** dev-core's Babel invocation passes `--ignore='**/test/data/**' --ignore='**/test-data/**'`; `core-server`'s does not. dev-core brings test-data fixture trees (`src/projects/handlers/_lib/test/data/`, `src/work/handlers/_lib/test/data/`, and others) whose contents are `.txt`/`.json`/`.yaml`/`.plain` — none of which Babel compiles by default, so `--ours` is very likely safe. But it is the one build-file resolution in the set with a plausible functional consequence, and the first `make test` after the merge is where it would show up. Worth an explicit check rather than an assumption.
- **`plugin-graph-gate.test.js`'s allowlist will need revision in Phase 3.** Its second entry names requirer nodeId `@sdlcforge/dev-core#orgs`, which stops existing once the components are re-declared under `@sdlcforge/core-server`. Phase 1's yalc-drift clearance already drops the first entry.
- **22 dev-core followups arrive with no home.** They are lost by the `--ours` resolution of `plan/followups.yaml` unless separately migrated. At least seven describe defects in code `core-server` is absorbing.
