# Build Wiring And Dependency Refresh

## Purpose and scope

The two mechanical questions this plan has to answer the same way twice — how the validation gate attaches to `core-server`'s Catalyst build, and how the yalc-linked framework build gets refreshed — worked out against this repository's real `make/` tree and its own documented yalc workflow.

## Build wiring

### What exists

`core-server`'s `Makefile` is Catalyst-generated and ends with:

```make
ifneq ($(wildcard make/*.mk),)
include make/*.mk
endif
```

`make/` currently holds nine fragments: `10-locations.mk`, `10-resources.mk`, `15-data-finder.mk`, `20-js-src-finder.mk`, `50-sdlcforge-server-exec-js.mk`, `50-sdlcforge-server-js.mk`, `55-lint.mk`, `55-test.mk`, `95-final-targets.mk`. Every one carries a "generated by @liquid-labs/catalyst-*" banner.

`95-final-targets.mk` defines the target algebra this plan depends on:

```make
build: $(BUILD_TARGETS)
test:  $(TEST_TARGETS)
lint:  $(LINT_TARGETS)
qa:    test lint
```

`package.json` maps `bun run build` → `make`, `bun run test` → `make test`, `bun run qa` → `make qa`, and `bun run lint` → `make lint`.

### The fragment

The upstream plan wires its own self-check the same way and states the recipe; this plan follows it rather than inventing a second pattern:

```make
# make/56-plugin-graph.mk -- hand-authored, not Catalyst-generated
CATALYST_PLUGIN_GRAPH_MARKER:=$(QA)/.plugin-graph.passed
TEST_TARGETS+=$(CATALYST_PLUGIN_GRAPH_MARKER)
```

Four properties of that choice, each load-bearing here:

- **`TEST_TARGETS`, not `BUILD_TARGETS`.** `qa: test lint`, so appending to `TEST_TARGETS` puts the gate in `make test` *and* `make qa` — both entry points the change request names — with one line and no edit to `95-final-targets.mk`.
- **No dependency on `dist/`.** The gate reads `package.json` and `node_modules`, both present immediately after install. Making it depend on the build would mean a broken plugin graph could only be discovered after a successful build, which inverts the point.
- **`56` is deliberate.** It sits in the gap the Catalyst generator leaves between the `55-*` fragments and `95-final-targets.mk`, so `include make/*.mk` picks it up in the right order with no edit to any generated file. `$(QA)` is already defined by `10-locations.mk` as `qa`.
- **The banner is inverted on purpose.** Every other fragment says "generated"; this one must say "hand-authored, not Catalyst-generated," or a future Catalyst regeneration pass reads it as stale output and removes it.

### Which entry point the marker's recipe calls

Two candidates, and the upstream task that ships them raises the same wrinkle for its own self-check:

- **The `plugable-express-validate` CLI**, via `node node_modules/.bin/plugable-express-validate` or the resolved bin path. Exercises exactly what CI would run, including argument parsing and exit codes. Depends on the framework's `dist/` bin having been built and installed.
- **`validatePluginSet()` from a Jest test**, driven through the existing `55-test.mk` machinery. No dependency on the framework's built bin, and it can assert on the structured result rather than parsing text.

They are not exclusive and the honest answer is likely both: the Jest test for the assertions, the marker for the gate. Whichever is chosen, the fragment's comment must say why, since the next reader will otherwise re-derive it.

**The exit-code contract matters to the recipe.** `0` clean, `1` validation failure, `2` resolution failure — and `2` means "I could not tell," not "your graph is fine." A recipe that treats any non-zero uniformly is correct for gating but loses the distinction in the log; a recipe that only checks for `1` would let a resolution failure pass silently. Fail on both, report which.

### A hazard specific to this repository

`55-test.mk` runs Jest from `$(TEST_STAGING)` over Babel-transpiled output, not from `src/`. A Jest-driven gate therefore resolves `node_modules` and `package.json` relative to `test-staging/`, not the package root. `validatePluginSet({ packageRoot })` defaults to `process.cwd()`, so the test must pass an explicit `packageRoot` pointing at the real package root. Getting this wrong yields a `resolution-failure` (exit `2`) that looks like a framework bug and is not.

The same asymmetry already shapes `src/lib/app-init.mjs`, which resolves its own `package.json` by trying `../package.json` (prod/bundled) and falling back to `../../package.json` (test/Babel-staged). That existing two-candidate probe is the precedent to follow, and the `plugable.host` block will be read out of the very same file `app-init.mjs` already parses at module scope — so the block is a property access away from code that already holds the parsed object.

## Dependency refresh

**Updated 2026-09-01** ([2026-09-01-blocker-reverification.md](./2026-09-01-blocker-reverification.md)): this section originally described a single-package (`plugable-express`-only) refresh. As of the re-verification pass, **two** local `.yalc`-linked packages are stale and both must be refreshed together before Phase 1's downstream tasks can run against real APIs: `@liquid-labs/plugable-express` (local `alpha.58` vs. published `alpha.59`) and `@sdlcforge/dev-core` (local snapshot dated 2026-08-27, predating dev-core's own `"plugable"` manifest block that merged 2026-09-01). `scripts/provision-local-deps.sh`'s `REQUIRED_YALC_PACKAGES` list already names both packages — it was updated as part of the dev-core-consolidation landing — so no script edit is needed, only the push-and-reinstall sequence below.

### The rule

`AGENTS.md` and `CLAUDE.md` both state it, and it is not optional:

> After any `yalc push` that changed the linked package's own `dependencies`, run `rm -f bun.lock && bun install` (or `./scripts/provision-local-deps.sh --refresh-lock`).

The reason is a Bun behavior with no workaround: once `bun.lock` holds a resolved entry for a `file:` spec, a bare `bun install` re-copies the linked package's **content** but does not re-resolve its own **dependency list**. `--force`, `--no-cache`, and a version bump are all equally ineffective. A newly added transitive dependency simply never materializes while `bun install` reports success. This applies identically to both stale packages — a single `rm -f bun.lock && bun install` (or one `--refresh-lock` run) after both `yalc push`es covers both at once; it does not need to run twice.

### Why it is load-bearing for this plan specifically

The `plugable-express` build this plan consumes adds, at minimum, a `bin` entry (`plugable-express-validate` → `./dist/plugable-express-validate.js`). A `bin` is not a dependency, but the same task may add dependencies, and the failure mode is silent success — the worst kind to debug through a `make` failure. The `dev-core` refresh is load-bearing for a different reason: without it, `node_modules/@sdlcforge/dev-core/package.json` carries no `"plugable"` block at all, which Phase 3's verification work depends on being present and correct. The refresh is cheap and the diagnosis is not, so this plan treats it as a required step rather than a conditional one.

**Symptom to expect if the `plugable-express` half is skipped:** the `plugable-express-validate` bin is absent from `node_modules/.bin/`, or `import { validatePluginSet } from '@liquid-labs/plugable-express'` resolves to `undefined`, while `bun install` reported success and `.yalc/@liquid-labs/plugable-express/dist/` visibly contains the new code.

**Symptom to expect if the `dev-core` half is skipped:** `node_modules/@sdlcforge/dev-core/package.json` has no `"plugable"` key, while `bun install` reported success and the real `dev-core` checkout's `package.json` visibly has one.

### The sequence

1. In `plugable-express`: `yalc push`. Its `prepack` runs `make build`, so the pushed `dist/` is freshly built — no separate build step is needed on that side. The framework itself is already merged and published; nothing to land first.
2. In `dev-core`: `yalc push`, the same way — its `"plugable"` manifest block is already merged on `main`.
3. In `core-server`: `rm -f bun.lock && bun install`, or `./scripts/provision-local-deps.sh --refresh-lock` — one pass covers both packages pushed in steps 1-2.
4. Verify the uptake rather than assuming it, for **both** packages — the `plugable-express-validate` bin is present in `node_modules/.bin/`, the `@liquid-labs/plugable-express` package exports `validatePluginSet` and `verifyHostDeclaration`, and `node_modules/@sdlcforge/dev-core/package.json` carries a `"plugable"` key.
5. `bun run build` to confirm nothing regressed.

Step 4 is the one worth insisting on, for both packages. It is the same check the prerequisite-verification task at the head of Phase 1 performs, and it is cheap enough to repeat.

### Task-worktree provisioning

`.yalc/` is gitignored and absent from every fresh Flow task worktree, so any task in this plan that runs `bun install`, `make test`, or `make qa` needs the documented provisioning sequence first:

```bash
create-worktree.sh --no-install-deps …
cd "$WORKTREE_PATH" && /path/to/main-checkout/scripts/provision-local-deps.sh
```

This is existing project convention, not new work, but it applies to more tasks than usual here: this plan's validation steps are almost all "run the gate," and the gate reads `node_modules`.

`scripts/provision-local-deps.sh` carries its own `REQUIRED_YALC_PACKAGES` list, which `AGENTS.md` says to keep in sync with the `file:.yalc/…` entries in `bun.lock`. If the framework uptake changes that set, the script needs updating in the same task — re-derive with `grep -n 'file:\.yalc' bun.lock`.
