# Overview

## Purpose and scope

This is the "core-server-domain-consolidation" plan-group of the sdlcforge-modernization wave plan (wave: "Plugin Consolidation — Framework and Dev-Core", lead project: core-server). It federates four projects under one plan slug — liq-controls, liq-credentials, liq-integrations-issues-github (each a donor, originating a relocation of its own plugin source), and core-server (the fold-in target, which absorbs all three via git-history-preserving merge and retires each donor). This plan-group follows the same absorption convention already used by two completed sibling plan-groups in the same wave: "dev-core-consolidation" (which merged liq-projects/liq-work/liq-orgs/plugable-projects-audit into a new sdlcforge/dev-core package — see that package's [`docs/dev-core-consolidation-contract.md`](/Users/zane/playground/sdlcforge/dev-core/docs/dev-core-consolidation-contract.md) as the canonical model for the absorption recipe, layout convention, root-file ownership rules, and retirement policy) and "framework-consolidation" (which folded plugable-server-documentation and liq-integrations into plugable-express). Absorb behavior unchanged; document pre-existing defects rather than silently fixing them unless trivially in scope. A donor's retirement is documentation/metadata work only (README rewritten as a superseded notice, package.json description/version bump, an attempted npm deprecate) — never deletion of the repo, and never a re-export shim left behind if that would crash the server via duplicate route/path-variable registration. **That risk is confirmed to apply here**: `liq-controls` registers no path variables of its own, but both of its routes are array-style `path` registrations, and `plugable-express`'s command-path registration throws `Non-unique command path: <path>` on a second registration of the same path — a shim left alongside a landed absorption would crash server startup. See [source inventory](./notes/liq-controls-source-inventory.md) for the full analysis.

### This project's slice (liq-controls)

`liq-controls` is a `@liquid-labs/plugable-express` plugin (`@liquid-labs/liq-controls`, currently `1.0.0-alpha.9`) that "enables and manages policy controls" for a plugable-express server: it loads question-based policy control definitions (`*.qcontrols.yaml`) per organization at server setup, exposes them over two HTTP endpoints, and serves them to other plugins through a `getQuestionControls` integration hook. It declares `@liquid-labs/liq-projects` and `@liquid-labs/liq-orgs` as plugin-level dependencies in `plugable-express.yaml`, and — confirmed directly from source, not merely assumed from the wave manifest's description — reads `app.ext._liqOrgs.orgs` (in `load-controls.mjs` and `get-question-controls.mjs`) and `app.ext._liqProjects.playgroundMonitor` (in `get-question-controls.mjs`). Both names are on `dev-core-consolidation-contract.md`'s `app.ext` contract freeze list, which names these exact two `liq-controls` files as outside readers of that contract — this plan's relocation must not disturb what they read. `liq-controls` gained a first `README.md` and `docs/liq-controls-spec.md` shortly before this plan-group's own planning pass began (authored via `gather-project-definition`/`dispatch-doc-author` so the fold could be scoped against real documentation instead of an undocumented codebase; both are committed to `main`) — Phase 2 task 2 below rewrites, rather than freshly authors, that README as the final superseded notice. Its sole npm dependent, confirmed by a playground-wide grep, is `@sdlcforge/core-server` itself (row 1 of the 11-entry `explicitPlugins` tier-2 list in `docs/architecture/plugin-loading-tiers.md`).

This plan's scope is `liq-controls`'s own slice only: relocate its plugin source in place to the shape the eventual absorption into `core-server` will merge, leave a thin re-export behind so the package stays independently green and publishable in the interim, and prepare (but gate) its own retirement. It does **not** plan `core-server`'s own merge-and-wire phase — that is `core-server`'s own slice of this same federated plan, authored separately (dispatched after this project and the other two donors, in this same multi-project authoring pass) — mirroring exactly what the `dev-core-consolidation` sibling plan-group's donor-side projects (`liq-work`, `liq-orgs`) did in their own plans before `dev-core` absorbed them. `liq-orgs`'s own finalized plan (`liq-orgs`'s `plan/plan-summary-dev-core-consolidation.md`) is the closest available precedent for this shape and is followed closely below, including its use of a read-only verification gate as the first task of the retirement phase to enforce the "retirement must not complete before the absorbing project's absorption has landed" ordering — a phase-level, self-contained mechanism rather than a cross-project scheduling dependency this plan cannot itself enforce.

Full findings (route surface, `app.ext` contract, npm dependents, pre-existing defects, and flagged anomalies) are in the [source inventory](./notes/liq-controls-source-inventory.md).

## Overview

Two phases, strictly sequential.

### Phase 1 — Relocate Plugin Source

Relocates `liq-controls`'s entire `src/` tree in place to its final core-server-relative path (`src/controls/…`), reduces the root build-entry file (`src/lib/index.js`) to a thin re-export, and keeps the package independently green (`make build`/`make test`/`make lint`) throughout. One task:

1. **`001-restructure-src-into-core-server-layout.md`** (tier `sonnet-high`) — `git mv` all 19 source files into `src/controls/…`, add `src/controls/index.js` as the new submodule public surface (verbatim moved content), reduce `src/lib/index.js` to `export * from '../controls'`, update `make/01-schema.mk`'s `SCHEMA_SRC` to the new schema path, and verify route parity, build, test, and lint all pass at the pre-move baseline.

### Phase 2 — Retire Liq-Controls

Follows the shape established by `liq-orgs`'s own dev-core-consolidation retirement phase: verify the absorption first, then documentation and metadata, then the publish attempt. No code deletion, no re-export shim. Four tasks, task 1 gating the rest:

1. **`001-verify-core-server-absorption.md`** (tier `sonnet-med`) — read-only gate: confirms `core-server` actually carries `liq-controls`'s complete relocated tree, byte-identical route `path` arrays, the `getQuestionControls` hook still registered, `core-server`'s own `package.json` no longer declaring a direct `@liquid-labs/liq-controls` dependency, and `core-server`'s build/test/lint green. Halts the phase on any gap; edits nothing.
2. **`002-author-readme-superseded-notice.md`** (tier `sonnet-med`) — rewrites the existing `README.md` (see "This project's slice" above) as the final superseded notice: superseded banner naming `@sdlcforge/core-server`, an accurate statement of what the package did, the confirmed single-consumer inventory, and disclosure of the three pre-existing defects recorded in the source inventory.
3. **`003-mark-package-deprecated-and-bump-version.md`** (tier `sonnet-low`) — `package.json` only: deprecation-leading `description`, version bump, `make qa` green.
4. **`004-publish-final-and-deprecate-on-npm.md`** (tier `sonnet-low`) — attempts `npm publish` and `npm deprecate`; hands the exact commands to the user if the environment blocks either. Repository archival is left as an explicit, separate human decision.

**Dependencies:** Phase 1 → Phase 2 (Phase 2 task 1 gates tasks 2–4; tasks 2 and 3 are parallel-eligible once task 1 passes — disjoint files, `README.md` vs. `package.json`). Phase 2 as a whole is additionally gated on `core-server`'s own absorption phase landing, a cross-project ordering constraint this plan cannot enforce through its own tooling — flagged to the dispatching manager (see this skill's structured report).

No `## Metadata` / `architectural_impact` flag applies to any task in this plan: no public API or component boundary changes (routes and behavior are explicitly unchanged), no new subsystem, no spec-defined behavior change, and no tracked-state addition or removal. The [architectural implications check](#) accordingly registers no `doc-updates` phase.
