# Absorb Dev-Core

## Purpose and scope

Phase 2 of the `sdlc-core-unification` plan. Performs the git-history-preserving merge of `@sdlcforge/dev-core` into `@sdlcforge/core-server`, resolves package-level file ownership, re-files the donor's still-live followups, and unions the dependency sets — without wiring anything, so the merge is independently reviewable and revertible before behavior moves.

## Goals

1. **Merge with history preserved.** `git merge --allow-unrelated-histories` keeps the donor's full history reachable under the absorbed paths, so `git log --follow src/projects/setup.mjs` still reaches the original commits. This is the whole reason a merge is used rather than a copy, and it is verifiable rather than assumed.

   The recipe's step-1 donor-side relocation is **not needed**: dev-core's `main` already carries `src/{projects,orgs,work,projects-audit}/…`. Confirm that with `git ls-tree -r --name-only dev-core-source/main -- src` before merging — merging a pre-restructure tree writes every file to the wrong path and has to be undone by hand.

2. **Resolve the 14 `add/add` conflicts in `core-server`'s favor — and then handle the clean arrivals git never asks about.** The arrival map is measured, not projected: the [merge-arrival inventory](../notes/merge-arrival-inventory.md) ran this merge in a throwaway clone and classified every path. **Correction (2026-09-06):** the live merge measured **14** conflicts, not 13 — dev-core's `main` advanced one commit past this inventory's originally-measured tip, adding a `dependencies` scheduling annotation to its own `plan/manifest.yaml` entry that turned that path from a silent identical merge into a 14th `add/add` conflict (resolved `--ours`, nothing core-server needed to preserve; see [`plan/phase-02-absorb-dev-core/001-execute-absorption-merge.md`](../phase-02-absorb-dev-core/001-execute-absorption-merge.md)'s own correction for detail). Every other count is unaffected: **169** clean arrivals, **110** untouched `core-server`-only paths.

   **Correction to this phase's original premise.** This document previously asserted that both repositories' `Makefile`, `make/*.mk`, and `.gitignore` "descend from the same Catalyst generator, so a byte-identical fragment merges silently with nothing to flag it." That is **false, in the safer direction**. `core-server` is generated by `@liquid-labs/catalyst-lib-makefiles`/`catalyst-builder-node` (`CATALYST_*`); `dev-core` by `@liquid-labs/sdlc-projects-workflow-local-node-build` (`SDLC_*`). Every shared build file differs, and every one produces an `add/add` conflict git surfaces loudly. **Nothing in the build-file set merges silently.** The only path in the entire merge that merges silently is `plan/manifest.yaml`, byte-identical on both sides because the same wave tooling wrote it — a no-op needing no handling, and emphatically **not** residue to remove.

   This does not retire the contract's warning; it relocates it. The unreviewed-arrival hazard lives entirely in the clean-add set, so verification must be a blob comparison of every root-level path against Phase 1's recorded pre-merge map, aimed primarily at the 10 clean arrivals below.

   **The 14 conflicts.** `git checkout --ours` is the correct mechanical resolution for all 14, but four of them carry a decision that `--ours` alone silently discards, and those are not optional:

   - `package.json` — wholly different packages (`core-server`'s is a **host** declaration, dev-core's a **plugin** declaration). Take `--ours` mechanically, then apply the dependency union (goal 5) and the component declarations (Phase 3) as their own recorded steps. Never hand-merge inside the conflict marker.
   - `plan/followups.yaml` — a real conflict, **not** a clean arrival. `--ours` alone drops **22 live dev-core followups** against code this merge absorbs. See goal 3.
   - `README.md` and `docs/architecture.md` — both genuine content conflicts between two real, fully divergent documents. `--ours` for the merge commit, then fold dev-core's substance (its per-submodule route tables, the projects-audit → projects dependency section, the submodule decomposition, composite-`setup` ordering contract, and `app.ext` service contracts) into `core-server`'s during the `doc-updates` phase. Not a Phase 2 blocker, but it must be handed forward explicitly rather than lost in a `--ours`.

   The remaining nine (`.gitignore`, `Makefile`, `make/{10-locations,10-resources,15-data-finder,20-js-src-finder,55-lint,55-test,95-final-targets}.mk`) are `--ours` with nothing to carry forward. `.gitignore` was verified lossless — `core-server`'s 10 entries are a strict superset of dev-core's 6. One resolution has a plausible functional consequence and deserves an explicit check rather than an assumption: `make/55-test.mk`'s Babel invocation carries `--ignore='**/test/data/**' --ignore='**/test-data/**'` on dev-core's side and not on `core-server`'s, and dev-core brings test-data fixture trees. Their contents are `.txt`/`.json`/`.yaml`/`.plain`, which Babel does not compile by default, so `--ours` is very likely safe — the first `make test` after the merge is where it would show up.

3. **Re-file dev-core's still-live followups rather than dropping them.** `plan/followups.yaml` conflicts; `core-server` has 30 IDs, dev-core 22, with **no ID collisions**. At least seven describe defects in code `core-server` now owns and must not disappear into a `--ours`: `AhMK` (command injection in `work` shell-outs), `g23a` (same in `projects`), `bTGn` (inherited `projects-audit` defects), `X7IU` (`parameters-set` `setUndefined`/`setNull` errors), `ZkAv` (`orgs` `create.mjs` creates directory only), `2Zug` (`orgs` `list.mjs` mdFormatter field mismatch), and `Jbaz` (`parameters-list.mjs` formatter). Re-file through the followups tool against `core-server`'s registry — never by hand-merging YAML, and never by a blind `--ours`/`--theirs` pick. Triage the remaining 15 the same way: carry across what still describes live code or docs `core-server` now owns, and deliberately drop what was scoped to dev-core's own build (`AEsA`, the `sdlc-resource-*` deprecation) or to a plan that has already closed.

4. **Remove the arriving paths that have no `core-server` counterpart.** Ten clean arrivals need a decision; the other 159 are the absorbed component tree and need none. The `git rm` set is exactly:

   - `src/index.mjs` — dev-core's own plugin aggregator. This is the *inverse* of the contract's stated `projects-audit` hazard: `core-server` has no file at that path, so it arrives as a clean add rather than an add/add conflict, and `git rm` is correct here where it would have been catastrophic there. Its role is taken by `src/lib/builtin-plugins.mjs`. Verified: `src/lib/index.js` is untouched by the merge (blob `e8791e8`, identical to `main`) — the two live at different paths and never interact.
   - `make/50-dev-core-js.mk` — would add a third Rollup target building `dist/dev-core.js`, picked up automatically by `Makefile`'s `include make/*.mk`.
   - `.sdlc-data.yaml` — dev-core's generator inventory; `core-server`'s equivalent is the differently-named `.catalyst-data.yaml`, which survives untouched.
   - `package-lock.json` — `core-server` is on Bun and tracks `bun.lock`. Verified: `bun.lock` is untouched by the merge (blob `901e082`). The real risk here is the inverse of an overwrite — dev-core's lockfile sitting *alongside* `bun.lock` under a different name, inert but present, and misleading a later `npm install`.
   - `src/test/plugin-manifest.test.mjs` and `src/test/index.test.mjs` — see goal 5.
   - `plan/plan-summary-dev-core-plugin-manifest.md` and `plan/plan-summary-orgs-defects-remediation.md` — dev-core plan residue.

   **The `plan/` removal set is those two `plan-summary-*.md` files and nothing else** — narrower than this document originally stated. `plan/followups.yaml` is a conflict resolution (goal 3), and `plan/manifest.yaml` is not residue at all. dev-core's `main` tracks only those four `plan/` paths; its `plan/waves/`, `phases/`, `notes/`, `TODO.yaml`, and `resources/` live on a branch that is not a merge source.

   The hazard here is real rather than hypothetical, because the merge lands on `main` (or a unit-of-work branch cut from it), and **`core-server`'s `main` tracks 14 `plan/` paths of its own**. So: never `git rm -r plan/`; never `git rm plan/manifest.yaml` or `git rm plan/followups.yaml`.

   Two arrivals are deliberately **kept** through this phase: `docs/dev-core-consolidation-contract.md` (this phase's own cited recipe — deleting it in the commit that follows it is self-defeating) and `docs/consumer-migration.md` (documents repointing away from superseded donor packages). Both are decided in the `doc-updates` phase alongside `docs/architecture.md`, not here.

5. **Drop dev-core's two package-level test suites, carrying one forward.** Both arrive clean, and both **will** be collected — `core-server`'s Jest config leaves `testMatch` at the default, and the `repoRoot` walk in `plugin-manifest.test.mjs` still resolves under `core-server`'s identical `src` → `test-staging` layout. Nothing fails mechanically; the failures are premise failures. The dispositions are settled, not open:

   - `src/test/plugin-manifest.test.mjs` — **drop outright. Do not port.** It is a drift guard over `plugable.components[…]`, a **plugin-side** manifest shape `core-server` does not have and will not have. Measured against the real post-merge conditions its 17 assertions split into 4 hard failures, **12 vacuous passes** (every `test.each` satisfaction case asserts the *absence* of a finding, so all twelve pass against an empty finding set — a ported version would go green on an empty graph), and 1 incidentally-true check. Its job is already done, and done better, by `core-server`'s existing `src/lib/test/host-declaration.test.js` and `src/lib/test/plugin-graph-gate.test.js`, which run over the real resolved graph rather than a `package.json`-only slice.
   - `src/test/index.test.mjs` — **`git rm` here, port its assertions in Phase 3.** It cannot survive this phase in any form (its first import is `from '../index'`, which goal 4 removes), and its aggregate assertions have nothing to assert against yet — at merge time the four absorbed submodules are still absent from `builtin-plugins.mjs`' `submodules` array. Record in the commit message that its assertions are carried into Phase 3's scope.

   Note the test-count consequence of the merge itself: **20 of the 159 absorbed component-tree paths are `*.test.mjs`/`*.test.js` suites** that Babel transpiles into `test-staging/` and Jest executes from the moment the merge lands, on top of `core-server`'s current 17. Goal 7's "leaves the system working" gate has to account for 20 newly-executing suites, not just the two named above.

6. **Union the runtime dependencies, then regenerate the lockfile the Bun way.** The union is measured and tabulated in the [dependency-union research](../notes/dependency-union.md#the-resolved-union-table): 22 + 23 names, 12 overlaps, **32** after dropping `@sdlcforge/dev-core`. Six overlaps move up, one (`@liquid-labs/liq-credentials-db`) `core-server` already wins and must be kept, five are identical.

   **The six upward moves are low-risk, and that was measured rather than argued.** Because dev-core is already consumed through a `file:` yalc link, `bun.lock` already resolves all six at or above the higher floor today — the union changes the declaration, not the installed tree, and introduces **zero** new resolved versions. An exhaustive symbol-by-symbol check of all 18 bare specifiers in `core-server/src/` against the packages actually installed for them produced exactly one failure, and Phase 1 goal 1 has already fixed it.

   Two mechanical traps to avoid: prerelease identifiers compare **numerically, not lexically** (a string-sorted union gets `@liquid-labs/shell-toolkit` backwards — `alpha.10` beats `alpha.7`), and a caret on a prerelease is far wider than it looks (`^1.0.0-alpha.15` expands to `>=1.0.0-alpha.15 <2.0.0-0`).

   Do not carry dev-core's `_npm-check-plus.depcheck.ignoreMatches` block across verbatim: its `@liquid-labs/sdlc-resource-*` glob is inert in `core-server`, whose resources are the `@liquid-labs/catalyst-resource-*` family. Rewrite the glob or drop the block deliberately.

   The lockfile refresh is `rm -f bun.lock && bun install` (or `scripts/provision-local-deps.sh --refresh-lock`), never the recipe's literal `package-lock.json` step and never `npm install`: under Bun, a bare `bun install` does not re-resolve a linked package's transitive dependency list once `bun.lock` holds a resolved `file:` entry. **Treat that refresh as its own reviewable step** with its own commit and its own read of the resulting diff — it floats ~20 caret-on-prerelease ranges, a far wider blast radius than the union it serves. One drift is known and already cleared as safe: `@liquid-labs/plugable-defaults` moves from `1.0.0-alpha.4` on disk to `1.0.0-alpha.7`, and both versions export the only symbol the absorbed code uses.

   **Do not apply the recipe's `grep -n 'file:' package.json` gate literally.** The correct post-union expectation is **exactly one** surviving hit — `@liquid-labs/plugable-express`, a pre-existing yalc link this plan neither creates nor touches — plus `@sdlcforge/dev-core` until Phase 3 removes it. Any task phrasing this check as "zero `file:` hits" is wrong and will send an implementer to "fix" `core-server`'s documented local-development mechanism.

7. **Leave the system working and unchanged in behavior.** At phase end the absorbed source sits in tree but is inert: `builtin-plugins.mjs` still aggregates three components and `@sdlcforge/dev-core` is still an explicit npm plugin, so the server still registers 165 routes with the same provenance as before. Snapshots must not move in this phase.
