# Component Boundary Hardening

## Purpose and scope

Phase 5 of the `sdlc-core-unification` plan. Makes the internal component boundary mechanically enforced rather than merely documented, now that seven components share one package and the package boundary that used to separate four of them is gone.

This phase is **substantially smaller than originally scoped.** The [ESLint component-boundary research](../notes/eslint-component-boundary-rule.md) did not just settle the mechanics; it wrote the rule, ran it against a real assembled post-merge tree, and found zero pre-existing violations on either side. Two of the five original goals dissolve entirely: no build-wiring work exists, and no remediation work exists.

## Goals

1. **Forbid cross-component imports across all seven `src/<component>/` directories** with `import/no-restricted-paths`, configured as **seven zones — one per component**, each zone's `from` listing the other six. This is new hardening beyond what either predecessor enforced, and it is the direct replacement for the enforcement the package boundary used to provide for free.

   The rule choice is settled and is not a matter of taste. `no-restricted-imports` with `patterns` is the **wrong** tool: it matches the specifier *text*, and component names recur as ordinary nested directory names inside other components (`src/controls/handlers/orgs/`, `src/controls/handlers/orgs/controls/`, `src/work/handlers/projects/`, `src/work/handlers/issues/`). A pattern like `**/orgs/**` flags `src/controls/handlers/index.js`'s entirely legitimate `export * from './orgs'`. `import/no-restricted-paths` matches on the **resolved absolute path** of the import target and applies a zone only to files inside that zone's own `target` — both properties are exactly what this boundary needs. It ships with `eslint-plugin-import@2.32.0`, already present via the Catalyst config's `extends: ['standard']`, so no new dependency is added.

   One zone per component rather than one zone listing all seven is also load-bearing: the rule builds one validator per `from` entry and reports if any matches, so a single zone with all seven in both `target` and `from` would flag every *within*-component import. `target`/`from` entries must stay plain directory paths, never globs — a zone whose `from` list `is-glob` reads as a glob degrades to reporting every import in the zone.

   Both existing manifests already declare the contract this rule formalizes. `dev-core`'s consolidation contract states it as prose — "No cross-submodule imports are introduced. The four source packages never imported each other; their coupling was, and remains, entirely through runtime `app.ext` state" — and both manifests encode it as data, through `provides`/`requires` capability declarations that name only `appExt:`, `pathVar:`, `setupMethod:`, `integration:`, and `credential:` capabilities, never a module path. Nothing has ever checked it. The rule matters more after this merge than before it, because the merge removes the thing that made violation impossible: before, `src/controls/` physically could not import from `dev-core`'s `orgs` without an npm dependency edge; after, `../orgs/` is a two-token relative path away.

2. **Take the exemptions structurally rather than by allowlist.** `src/lib/builtin-plugins.mjs` is not inside any zone's `target`, so its seven aggregation imports are exempt as a consequence of the zone shape — no `except` clause, no ignore comment, no allowlist to maintain. The same holds for `src/lib/test/builtin-plugins.test.js` and everything else under `src/lib/` and `src/cli/`. Within-component imports at any depth and bare `@liquid-labs/*` specifiers are likewise exempt structurally (bare specifiers resolve into `node_modules`, which no zone's `from` contains).

   This was verified rather than assumed, and the verification method matters because a negative test alone would be worthless: the rule silently does nothing when resolution fails, so "no findings" could equally mean "the imports never resolved." A **positive probe** — a temporary extra zone targeting `src/lib` — reported all seven `builtin-plugins.mjs` imports plus three in its test, confirming every extensionless directory specifier resolves (including the absorbed components' `.mjs` index files). Independently, `import/no-unresolved` over the whole 201-file merged tree produced zero findings.

3. **Introduce the rule at full strength on day one.** The pre-existing-violation sweep is **already done, and both component sets are clean**: zero `import/no-restricted-paths` findings across `src/controls/`, `src/credentials/`, `src/integrations-issues-github/`, `src/projects/`, `src/orgs/`, `src/work/`, and `src/projects-audit/`. So `error`, no allowlist, no `except`, no grandfathering, and **no remediation task and no followup for a pre-existing violation** — that contingency does not arise. Two cases are worth re-checking by name during implementation, because they are exactly what a weaker rule would get wrong and their continued cleanliness is the proof the right rule was used: `src/controls/handlers/index.js:1`'s `export * from './orgs'`, and `src/controls/handlers/orgs/controls/_lib/test/list-lib.test.mjs:6`'s five-levels-up-then-back-down import.

   Six evasion shapes were planted and all six reported: plain relative into a sibling's internals, leave-and-re-enter (`../../../src/orgs/...`), a sibling's public `index` surface, dynamic `import()`, CommonJS `require()`, and `export … from`.

4. **Add `.eslintrc.cjs` at the repo root and change nothing else.** There is **no build-wiring work in this phase.** The original premise — that reaching a project-local config would need a hand-authored `make/56-*` fragment in the `make/56-plugin-graph.mk` style — turned out to be unnecessary: ESLint 8.57.1 runs here in **eslintrc mode** (no flat config anywhere in the project or above it), and in that mode `make/55-lint.mk`'s `--config $(CATALYST_ESLINT_CONFIG)` is **additive**, merging on top of the `.eslintrc.*` cascade rather than replacing it. Verified by running the exact `make/55-lint.mk` invocation against an assembled post-merge tree: both rulesets fired in one run. `root: true` in the local file does not suppress the `--config` layer, and restating `plugins: ['import']` alongside `standard`'s own declaration is accepted.

   Catalyst does not generate or overwrite any ESLint config in a consuming project — `.catalyst-data.yaml` names exactly ten generated paths (`Makefile` plus nine `make/*.mk` fragments), and no `@liquid-labs/catalyst-*` package mentions `eslintrc` at all — so the file is safe to hand-author and will not be regenerated away. Carry the `make/56-*` precedent's *shape* (an in-file header comment saying it is hand-authored and why) without needing its mechanism. The research note carries the complete proposed file, including its `COMPONENT_DIRS` list; note that list is **directory** names, so the third entry is `integrations-issues-github`, not the manifest's `issues-github`. Set `basePath: __dirname` so zone paths mean the same thing from the repo root, a subdirectory, or an editor integration.

   The fallback path — a `make/56-lint-boundary.mk` redirecting `CATALYST_ESLINT_CONFIG` — was also proven to work and is recorded in the note, but it *replaces* rather than layers and silently diverges the moment Catalyst's config changes. It is insurance against a future ESLint 9 / flat-config move, not the plan.

5. **Guard against the rule going silently inert.** One failure mode is loud and acceptable: an `eslint.config.js` appearing at the repo root or any ancestor flips ESLint to flat mode, `.eslintrc.cjs` becomes inert, `--config` is handed an object it cannot validate, and `make lint` fails hard. The other is silent: a future ESLint 9 upgrade inside `catalyst-resource-eslint` that ships a real flat config would make the rule inert while the run still succeeds.

   Write `src/lib/test/component-boundary.test.js` with two assertions, both verified workable: a **liveness probe** that lints an in-memory cross-component import through the ESLint Node API (`new ESLint({ cwd, overrideConfigFile: CATALYST_CONFIG, useEslintrc: true })`, `lintText` against a `filePath` under `src/controls/` that need not exist on disk) and asserts an `import/no-restricted-paths` message comes back; and a **drift assertion** comparing the config's `COMPONENT_DIRS` against the actual directory set under `src/` minus `lib` and `cli`, so adding an eighth component without adding it to the rule fails the test rather than going unenforced. This is a third drift guard alongside Phase 3's component-order assertion; they may share a file.

6. **Settle two deliberate scope decisions rather than leaving them implicit.** Neither is a research gap; both are choices the implementing task must make explicitly and record:

   - **Whether to add `src/lib` and `src/cli` to every zone's `from`,** additionally forbidding a component from reaching into the host's own library and foreclosing the `lib → builtin-plugins → component → lib` cycle. No component imports `src/lib` today, so it costs nothing — but it enforces a *different* invariant than "components do not import each other," which is why it is called out rather than folded in. Adopt explicitly or drop explicitly.
   - **Whether a sibling's public `index` surface stays forbidden.** The proposed rule forbids it, which is the correct reading of the consolidation contract: components couple through `app.ext` and declared capabilities, never through module paths, public or not. Loosening it (adding sibling `index` files as zone `except` entries) is a deliberate decision, not an oversight to patch quietly.

7. **Introduce no new lint findings.** `make lint` reports a standing **233** pre-existing errors (230 in `test/`, 3 `'beforeAll' is not defined` in `src/lib/test/plugin-graph-*.test.js`; followups `b3hk`, `mLm3`), unrelated to this work and out of scope to fix. Running the merged seven-component tree with the proposed `.eslintrc.cjs` in place produced exactly those same 3 `src/` findings and nothing else — including when `.eslintrc.cjs` itself was linted, which `eslint .` with `--ext .cjs` does, and it passes clean. So "zero new findings" is a measured baseline to reproduce, not a hope. A further 239 findings appear under `plan/` and `worktrees/`; they are an artifact of the plan worktree living inside the repo and are absent from a clean checkout, so scope any count to `src/` and `test/`.

## Inputs

- Phase 3's output: seven components at `src/{controls,credentials,integrations-issues-github,projects,orgs,work,projects-audit}/`, with `src/lib/builtin-plugins.mjs` importing each one.
- Phase 4's green build, so a new lint failure is unambiguously attributable to this phase.
- [`notes/eslint-component-boundary-rule.md`](../notes/eslint-component-boundary-rule.md) — **complete**. Carries the literal `.eslintrc.cjs` (which itself lints clean under the Catalyst config), the config-resolution chain, the verified additive-`--config` behavior, the liveness-probe code, both sweep results, and the baseline arithmetic. It is the implementation source for this phase, not background reading.
- `make/55-lint.mk` and `make/10-resources.mk` — read to confirm the invocation is unchanged; **not edited**. `make/55-lint.mk`'s duplicated `.cjs` in `--ext .cjs,.js,.mjs,.cjs,.xjs` is harmless, generated, and out of scope — noted only so nobody "fixes" a generated fragment.
- The `provides`/`requires` declarations in `package.json`'s `plugable.host.builtins[0].components`, which state the sanctioned coupling the rule enforces the complement of.

## Outputs

- `.eslintrc.cjs` at the repo root carrying the seven-zone `import/no-restricted-paths` rule, layered over the Catalyst config, with a header comment recording that it is hand-authored, that Catalyst will not overwrite it, and why `--config` composes with it. **No `make/*.mk` file is added or edited.**
- `src/lib/test/component-boundary.test.js` with the ESLint-API liveness probe and the component-list-versus-`src/`-directories drift assertion.
- `make lint` failing on a deliberately-introduced cross-component import and passing without one — demonstrated, not assumed.
- A recorded decision on each of goal 6's two questions.
- Confirmation that this phase's additions contribute zero findings above the standing 233 (`src/` stays at 3, `test/` at 230), with no pre-existing violation found in either component set and therefore no remediation and no followup.

## Notes on sequencing

Parallel-eligible with Phase 4: this phase touches lint configuration and a new test file, while Phase 4 touches snapshots and the graph gate, and neither reads the other's output. It is listed after Phase 4 so that a failing plugin-graph gate is diagnosed against a clean lint baseline rather than alongside newly-introduced lint changes.
