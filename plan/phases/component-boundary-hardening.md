# Component Boundary Hardening

## Purpose and scope

Phase 5 of the `sdlc-core-unification` plan. Makes the internal component boundary mechanically enforced rather than merely documented, now that seven components share one package and the package boundary that used to separate four of them is gone.

## Goals

1. **Forbid cross-component imports across all seven `src/<component>/` directories** with an ESLint `no-restricted-imports` rule (or the equivalent `import/no-restricted-paths`, whichever the project's configured plugin set actually supports). This is new hardening beyond what either predecessor enforced, and it is the direct replacement for the enforcement the package boundary used to provide for free.

   Both existing manifests already declare the contract this rule formalizes. `dev-core`'s consolidation contract states it as prose — "No cross-submodule imports are introduced. The four source packages never imported each other; their coupling was, and remains, entirely through runtime `app.ext` state" — and both manifests encode it as data, through `provides`/`requires` capability declarations that name only `appExt:`, `pathVar:`, `setupMethod:`, `integration:`, and `credential:` capabilities, never a module path. Nothing has ever checked it.

   The rule matters more after this merge than before it, because the merge removes the thing that made violation impossible. Before, `src/controls/` physically could not import from `dev-core`'s `orgs` without an npm dependency edge; after, `../orgs/` is a two-token relative path away.

2. **Get the exemptions right.** The rule must forbid `src/<a>/**` importing `../<b>/` for any two distinct components among the seven, while continuing to permit:

   - `src/lib/builtin-plugins.mjs` importing each component's directory — that aggregation is the mechanism, and a rule that breaks it is wrong;
   - within-component imports at any depth (`src/work/handlers/_lib/…` importing `../../setup.mjs`);
   - bare-specifier imports of shared `@liquid-labs/*` libraries, which are the sanctioned sharing mechanism.

   A rule that produces even one false positive against existing, correct code will be worked around rather than fixed, so scoping it precisely is the substance of this phase, not an afterthought.

3. **Establish whether the boundary currently holds.** The rule is being added to a tree that has never been checked against it. Two independently-developed component sets have just been merged; if any pre-existing violation exists it will surface here for the first time. Finding one is a legitimate outcome — it is either fixed within this phase's scope or recorded as a followup with the rule scoped to fail on new violations only, but it is not a reason to weaken the rule silently.

4. **Wire it so it actually runs, without hand-editing a generated file.** `make/55-lint.mk` invokes ESLint with `--config $(CATALYST_ESLINT_CONFIG)`, which `make/10-resources.mk` resolves to `node_modules/@liquid-labs/catalyst-resource-eslint/dist/eslint.config.js` — a file inside a dependency, and resolved from a Catalyst-generated makefile fragment that a regeneration pass would overwrite. Neither is editable in place.

   The precedent for solving exactly this shape of problem already exists in this repository: `make/56-plugin-graph.mk` is hand-authored, deliberately carries no "generated by" banner (so a regeneration pass does not read it as stale output and delete it), and is numbered into the gap between the `55-*` fragments and `95-final-targets.mk` so `include make/*.mk` picks it up with no edit to any generated file. A project-local ESLint config that imports and extends the Catalyst one, selected through an equivalently-numbered hand-authored fragment, follows that precedent directly. Confirming the mechanics — flat config versus eslintrc, whether the Catalyst config is composable, whether `--config` can be overridden this way — is what the ESLint rule-wiring research exists to settle.

5. **Introduce no new lint findings of its own.** `make lint` currently reports ~233 pre-existing errors confined to `test/*.js` (followups `b3hk`, `mLm3`), unrelated to this work and out of scope to fix. This phase must be able to state that its own additions contribute zero findings, which means distinguishing its output from that standing noise.

## Inputs

- Phase 3's output: seven components at `src/{controls,credentials,integrations-issues-github,projects,orgs,work,projects-audit}/`, with `src/lib/builtin-plugins.mjs` importing each one.
- Phase 4's green build, so a new lint failure is unambiguously attributable to this phase.
- The ESLint rule-wiring research (`plan/notes/eslint-component-boundary-rule.md`), outstanding at the time this summary was written.
- `make/55-lint.mk`, `make/10-resources.mk`, and `make/56-plugin-graph.mk` — the wiring being extended and the precedent being followed.
- The `provides`/`requires` declarations in `package.json`'s `plugable.host.builtins[0].components`, which state the sanctioned coupling the rule enforces the complement of.

## Outputs

- A project-local ESLint configuration carrying the cross-component import restriction, layered over the Catalyst config rather than replacing it.
- Build wiring that selects it, hand-authored in the `make/56-*` style, carrying no generated-by banner and an in-file note saying why.
- `make lint` failing on a deliberately-introduced cross-component import and passing without one — demonstrated, not assumed.
- A statement of whether any pre-existing violation was found, with either the fix or the recorded followup.
- Confirmation that this phase's additions contribute zero new findings above the standing ~233.

## Notes on sequencing

Parallel-eligible with Phase 4: this phase touches lint configuration and build wiring, while Phase 4 touches tests and snapshots, and neither reads the other's output. It is listed after Phase 4 so that a failing plugin-graph gate is diagnosed against a clean lint baseline rather than alongside newly-introduced lint changes.
