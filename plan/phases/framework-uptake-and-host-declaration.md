# Phase — Framework Uptake And Host Declaration

## Goals

Make `core-server`'s plugin set **statically visible** to the upstream validator, and prove the framework it depends on is actually present before anything is built on top of it.

Two things have to be true before a single capability can be declared. The framework must be installed in a build that carries the manifest surface, and `core-server`'s two undiscoverable plugin tiers must be declared as data. Neither the `builtinPlugins` entry nor the `explicitPlugins` array literal can be found by any scan: keyword discovery contributes exactly zero plugins to this project, so the array literals in `src/lib/app-init.mjs` and `src/lib/builtin-plugins.mjs` are the entire input a resolver has. Until they exist as a `plugable.host` block, the validator sees an empty set and reports a clean graph over nothing.

**Re-verified 2026-09-01, correcting the 2026-08-26 grounding pass** ([2026-09-01-blocker-reverification.md](../notes/2026-09-01-blocker-reverification.md)): the upstream framework's implementation is no longer merely designed — it shipped. `@liquid-labs/plugable-express` is built, tagged `v1.0.0-alpha.59`, and published to the public npm registry, carrying `validatePluginSet`, `verifyHostDeclaration`, `FRAMEWORK_MANIFEST`, the manifest reader, the graph engine, and the `plugable-express-validate` bin. Separately, the wave's sibling `dev-core-consolidation` plan-group finished: `core-server`'s real `explicitPlugins` array (`src/lib/app-init.mjs`, `main` branch) no longer lists `liq-orgs`/`liq-projects`/`liq-work`/`plugable-projects-audit` individually — it now carries **five** names, with those four absorbed into one `@sdlcforge/dev-core` entry — and a further `dev-core-plugin-manifest` plan-group merged `dev-core`'s own `package.json` `"plugable"` component manifest on 2026-09-01. **Neither of these facts has reached `core-server`'s local link yet.** `core-server`'s `.yalc/@liquid-labs/plugable-express/` snapshot is still `1.0.0-alpha.58` (dated 2026-08-24, zero occurrences of `validatePluginSet`/`plugable-express-validate`/`plugableManifestVersion`), and its `.yalc/@sdlcforge/dev-core/` snapshot is dated 2026-08-27 — before dev-core's manifest merged, so it carries no `"plugable"` block either. The remaining blocker is local and mechanical (a two-package `yalc push` + lockfile-refreshing reinstall), not an unmet upstream dependency; this phase's opening task performs it and halts and reports only if that refresh does not actually resolve `validatePluginSet`/`verifyHostDeclaration` and a manifested `@sdlcforge/dev-core`.

This phase comes first because it is the precondition for every other phase, and because it converts the plan's one external dependency from an assumption into a checked, halt-on-failure condition at the point where acting on it is cheapest.

It deliberately declares **structure without semantics**: the identity and load order of the participants, and nothing about what they provide or require. That keeps the drift guard (`verifyHostDeclaration()`, which compares the declaration against the real `builtinPlugins`/`explicitPlugins` arrays) meaningful from the first commit, before anyone starts trusting a declaration that could already have drifted. The upstream contract's own recommended migration order puts these two steps first for the same reason.

## Inputs

- **Two** `.yalc`-linked local dependencies, both stale in `core-server`'s local link and both required before any downstream Phase 1 task can run against real APIs:
  - `@liquid-labs/plugable-express` — the plugin-manifest reader, the host-declaration reader, the framework intrinsic manifest, `validatePluginSet()`, `verifyHostDeclaration()`, and the `plugable-express-validate` bin. Built and published (`v1.0.0-alpha.59`); `core-server`'s local snapshot is `alpha.58`.
  - `@sdlcforge/dev-core` — one of `core-server`'s five real `explicitPlugins` entries (absorbing the former `liq-orgs`/`liq-projects`/`liq-work`/`plugable-projects-audit`), whose own `package.json` `"plugable"` component manifest merged 2026-09-01. `core-server`'s local snapshot predates that merge and carries no `"plugable"` block.

  **This is a hard external prerequisite and, in `core-server`'s local link, it is not satisfied today** — not because either upstream deliverable is unfinished (both are), but because neither has been pushed and reinstalled locally yet.
- The upstream `docs/plugin-manifest-contract.md`, `docs/plugin-manifest-schema.md` (the `plugable.host` block's normative schema — [see the worked example](../notes/2026-09-01-blocker-reverification.md)), or the finalized design notes standing in for them.
- `src/lib/app-init.mjs` — the `explicitPlugins` array literal (**five** names on `main` as of the dev-core consolidation: `@liquid-labs/sdlc-projects-badges-coverage`, `@liquid-labs/sdlc-projects-badges-github-workflows`, `@liquid-labs/sdlc-projects-workflow-github-node-jest-cicd`, `@liquid-labs/sdlc-projects-workflow-local-node-build`, `@sdlcforge/dev-core` — not the eight-name list some earlier grounding notes, drafted before the consolidation landed, still describe) and the `package.json` object it already parses at module scope.
- `src/lib/builtin-plugins.mjs` — the `submodules` array (`controls`, `credentials`, `issuesGitHub`; unaffected by the dev-core consolidation, which only touched the explicit tier) whose order is normative load order, and the `builtinPluginsFor` aggregation policy.
- This project's documented yalc refresh workflow, and the task-worktree provisioning sequence that goes with it ([build-wiring-and-dependency-refresh.md](../notes/build-wiring-and-dependency-refresh.md), updated for the two-package refresh).

## Outputs

- A refreshed, verified pair of dependencies: `@liquid-labs/plugable-express`'s and `@sdlcforge/dev-core`'s manifest surfaces both resolvable from `core-server`, with `bun.lock` regenerated rather than reused, and `scripts/provision-local-deps.sh`'s `REQUIRED_YALC_PACKAGES` list (already lists both packages) reconfirmed against the yalc-resolved set.
- A `plugable.host` block in `core-server`'s `package.json` carrying `plugableManifestVersion`, the five real `explicitPlugins` names, and one `builtins` entry for `@sdlcforge/core-server` with its three components in `submodules` order — capability lists still empty.
- A drift guard in the Jest suite calling `verifyHostDeclaration()` against the real arrays, so a future edit to `explicitPlugins` or `submodules` that forgets the declaration fails `make test` rather than silently narrowing the validated set.
- A recorded statement of the derivation relationship between `submodules` and `components:`. Upstream flagged this as the residual hazard of the aggregated form — two transcriptions of one fact with nothing tying them together — and recommended deriving rather than restating. Whether that is achievable given the block lives in `package.json` (data) while `submodules` lives in `builtin-plugins.mjs` (code) is this phase's to settle; if it cannot be derived, the drift guard is the whole answer and must be treated as load-bearing.
- A resolution outcome for the plan as a whole if the prerequisite is unmet: the phase halts and reports rather than proceeding against a stub.
