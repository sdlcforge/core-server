# Phase 8 — liq-work Migration Into dev-core

## Purpose and scope

Phase summary for the migration phase of the `dev-core-consolidation` plan-group's `liq-work` slice. Task 001 executes in `liq-work` (`/Users/zane/playground/liquid-labs/liq-work`); tasks 002 and 003 execute in `sdlcforge/dev-core` (`/Users/zane/playground/sdlcforge/dev-core`).

## Goals

Move liq-work's code into `@sdlcforge/dev-core` as the `src/work/` submodule with no behavior change and its git history intact, port the best documentation any of the four donors has, and specify — without executing — the consumer swap `core-server` must perform.

The phase is split across two repositories on purpose, following the recipe `liq-projects` established and `liq-orgs` repeated: restructuring inside `liq-work` first, to the exact paths the code will occupy in dev-core, is what makes the absorption a plain `git merge --allow-unrelated-histories` with no path rewriting. History survives, the diff is reviewable, and the donor stays buildable and publishable while the transition runs.

Four things make this the **hardest** of the three absorptions run so far, and each shapes how the tasks are written:

- **It is the largest donor** — 69 tracked source files today (72 after phase 7), 30 handlers, 14 declared dependencies — and the flatten rule (`src/handlers/work/**` → `src/work/handlers/**`) moves 68 of them at once. But the relocation is near-pure: **exactly one import specifier changes** (`setup.mjs`'s `./handlers/work/_lib/work-db` → `./handlers/_lib/work-db`), because every other relative import either stays within one directory or moves uniformly with the subtree it points into.
- **It is the only absorption where D4's "take the higher range" rule actually fires.** Nine of liq-work's fourteen dependencies overlap an already-absorbed donor's, and in one case — `@liquid-labs/github-toolkit`, `^1.0.0-alpha.25` against liq-projects's `^1.0.0-alpha.20` — liq-work is **higher**, so the union effectively upgrades the `projects` submodule. Task 002 must verify that at the lockfile and re-run the `projects` suites rather than assuming it is a no-op.
- **The donor's `plan/` directory arrives cleanly.** A rehearsed merge confirms `plan/manifest.yaml` and two `plan-summary-*.md` files land with **no conflict** — so nothing prompts an agent to look at them, and Flow plan artifacts would silently enter dev-core. This is correction **C4**; the `liq-orgs` absorb task caught it, the `liq-projects` absorb task (which runs first) does not.
- **dev-core's `make test` is red before this phase starts and will be red after it ends.** The Node ≥ 24 `SlowBuffer` defect already fails 5 of the 8 suites `liq-projects` contributed; liq-work adds a sixth. Every gate in this phase is written against *"no new failures beyond the known set"*, measured against a baseline the task itself records — never against "green". The same defect makes the built bundle unloadable, so the route-parity check needs a `SlowBuffer` preload shim, supplied verbatim in each task and never committed.

**Validation cannot lean on the tests.** Coverage is 3.2% of statements; all 30 handlers and all 20 `_lib` modules sit at 0%. The real gates are static and structural: file census, `git diff -M` purity (one line of drift, mechanically verified), the 30-route/method parity diff written to files and `diff`ed, a no-duplicate-route sweep across the merged array, and `app.ext`/path-var assertions against a stub app. Each task says so rather than letting a suite result imply safety it does not provide.

Unlike `liq-orgs` — which had no documentation to port, only documentation to write — `liq-work` has an accurate, detailed README covering its domain model, all 30 routes, and its `app.ext` couplings. Task 002 ports its substance into dev-core, applying three corrections rather than copying stale claims through: `app.ext.integrations` is framework-owned (`plugable-express/src/app.js:112`) and not `liq-integrations`-owned; the "Modernization status" speculation is now history; and `submit-lib.mjs`'s guard covers the *hook*, not the presence of `app.ext.integrations`, which it dereferences unconditionally.

The consumer handoff is authored here rather than executed here because every consumer touch point lives in `core-server`, whose own plan-group (`core-server-domain-consolidation`) owns those edits (D11).
